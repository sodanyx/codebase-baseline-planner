## 1. 使用原则

本文件提供最低覆盖方向和开放式调查方法，不提供封闭清单。

执行时遵守：

- 从项目实际结构和证据出发，调整章节和调查深度；
- 先判断哪些因素真正影响运行、扩展、兼容和维护，再决定篇幅；
- 对高影响事项深入，对低价值事项压缩或省略；
- 不因某项内容未被点名就默认无需调查；
- 不因列出了很多条目就声称已经发现全部未知；
- 不要求所有项目都拥有相同的文档结构。

## 2. 项目特定覆盖图

正式分析前，先建立覆盖图。覆盖图不是目录复制，而是对当前项目的调查设计。

### 2.1 识别项目类型和关键成功条件

判断项目属于哪类系统，例如：

- 命令行工具、桌面应用、移动端、Web 服务、库或框架；
- 实时系统、数据管道、AI Agent、插件、游戏、自动化脚本；
- 单仓库、多包仓库、前后端分离、客户端与服务端组合；
- 活跃维护项目、停止维护项目、实验性项目或生产项目。

由项目类型推导真正重要的调查方向。例如桌面宠物可能更重视进程通信、状态同步、资源占用和窗口行为；库项目可能更重视公共 API、兼容性和语义版本。

### 2.2 形成调查矩阵

对每个调查领域记录：

- 调查问题；
- 重要性；
- 证据来源；
- 当前状态；
- 仍缺少的资料；
- 可能影响的后续决策。

### 2.3 开放式扩展

完成初始覆盖图后，从以下问题继续扩展：

- 如果没有用户给出的清单，维护者会首先检查什么？
- 哪些信息最容易被经验丰富的开发者默认为常识，却会让新 Agent 误判？
- 哪些问题只有在实际部署、跨平台运行或长期维护中才会暴露？
- 哪些领域一旦理解错误，会使整个改造方案建立在错误前提上？
- 当前项目是否存在特定领域规则，不能被通用软件工程清单覆盖？

## 3. 当前代码库调查

根据项目实际需要选择调查深度。以下内容属于最低覆盖候选，不是固定输出栏目。

### 3.1 项目目标与边界

调查：

- 项目要解决的问题和主要使用者；
- 明确支持、不支持和默认假设；
- 当前成熟度、维护状态和典型使用场景；
- 文档声称的目标与代码实际行为是否一致。

### 3.2 架构与运行链路

还原：

- 入口、初始化、主循环或请求生命周期；
- 模块和进程之间的调用、通信与依赖方向；
- 数据、事件、状态和控制流；
- 同步、异步、并发、缓存、队列、重试或调度机制；
- 正常路径、异常路径、退出与恢复路径；
- 关键扩展点、插件机制和替换边界。

不要只画静态模块图；必须说明系统从启动到产生结果实际发生了什么。

### 3.3 代码组织与约定

识别：

- 目录和重要文件职责；
- 主要类、函数、接口、数据结构和配置结构；
- 公共 API 与内部实现边界；
- 命名、类型、错误处理、日志和注释约定；
- 代码生成、脚手架、约定优于配置等隐含规则；
- 看似可修改但被其他模块隐式依赖的部分。

### 3.4 环境、依赖、构建与部署

调查：

- 语言、框架、运行时和版本要求；
- 直接、间接、可选和平台特定依赖；
- 配置来源、密钥、环境变量和默认值；
- 构建、打包、安装、升级、发布和部署流程；
- 操作系统、硬件、权限、网络和外部服务要求；
- 锁文件、版本漂移、废弃依赖和供应链风险。

### 3.5 数据、状态与外部接口

根据项目类型检查：

- 数据模型、持久化和迁移；
- 状态所有权、生命周期和一致性；
- 文件格式、协议、API、消息、插件和第三方服务；
- 输入验证、错误传播和兼容策略；
- 数据丢失、重复处理、顺序错误和恢复机制。

### 3.6 质量、测试与可观测性

检查：

- 单元、集成、端到端、回归和性能测试；
- 测试真正覆盖的路径与未覆盖部分；
- 可重复的最小运行或验证方法；
- 日志、指标、追踪、诊断开关和崩溃信息；
- CI 规则、质量门槛和常见失败模式；
- 文档中的测试说明是否仍适用于当前版本。

### 3.7 安全、性能与兼容性

仅在与项目相关时深入：

- 信任边界、权限、输入来源和敏感数据；
- 资源消耗、响应时间、并发和容量限制；
- 平台、版本、协议和数据向后兼容；
- 安全公告、危险默认值和已知攻击面；
- 为了性能或兼容作出的架构妥协。

## 4. GitHub 与项目历史调查

项目历史不是附录，而是理解设计决策、旧问题和维护风险的证据来源。

### 4.1 调查来源

在可访问时检查：

- Open 与 Closed Issues；
- 已合并、关闭、草稿和被拒绝的 Pull Requests；
- Discussions、Wiki、FAQ 和维护者回复；
- Releases、Tags、Changelog 和迁移说明；
- 与关键模块有关的提交和 blame 历史；
- Actions、构建失败、测试波动和发布失败；
- 安全公告、依赖升级和废弃功能；
- 重复反馈、平台差异和常见使用误区。

### 4.2 不把反馈直接当事实

对历史记录分类：

- 维护者确认且有修复或测试支持；
- 代码或运行结果可以复现；
- 仅有用户报告，尚未证实；
- 只影响特定版本、平台、配置或使用方式；
- 已修复且当前版本不再适用；
- 仍未解决或被暂缓；
- 属于设计限制而非缺陷；
- 已经过时或与当前分支不一致。

### 4.3 提取可复用经验

对高价值历史问题尽量记录：

- 问题来源和对应版本；
- 涉及模块、触发条件和可观察症状；
- 根因或维护者判断；
- 采用的修复、临时规避或拒绝方案；
- 为什么某种方案被接受或拒绝；
- 当前版本是否仍可能受影响；
- 二次开发中可能以何种不同形式复现；
- 哪些诊断或解决方法可以迁移到新问题。

重点不是罗列旧 Bug 数量，而是提取设计教训、调试路径、兼容知识和维护者决策依据。

### 4.4 评估历史可信度与时效性

始终核对：

- 记录对应的日期、分支和版本；
- 后续提交是否改变了结论；
- 讨论中的建议是否真的合并；
- 文档、Issue 和当前代码是否相互矛盾；
- 仓库是否存在长期无人维护、版本停滞或关键人员依赖。

## 5. 未知与盲区发现

把四类“已知与未知”当作扩大认知范围的透镜，而不是固定栏目：

- 用户已经明确表达的目标和约束；
- 用户知道自己还没解决的问题；
- 用户没有写出、但看到后会认可的隐含要求和常识；
- 用户与 Agent 都可能尚未想到的风险、能力上限或更优标准。

### 5.1 四轮发现过程

#### 证据扫描

交叉阅读代码、配置、测试、文档、运行结果和历史记录，识别互相支持或冲突的证据。

#### 隐含假设扫描

寻找没有写进文档但被代码、命名、测试、默认值或维护者行为体现的规则。

#### 失败反推

假设未来改造失败、运行异常、性能恶化、兼容破坏或新 Agent 误解，反推最可能遗漏了什么。

#### 范围外扫描

刻意寻找当前目录、分类和术语之外的高影响内容，尤其关注项目独有机制、外部依赖和跨模块连锁反应。

### 5.2 多视角检查

根据项目增加合适视角，例如：

- 第一次接手项目的 Agent；
- 长期维护者；
- 二次开发者；
- 最终用户或运维者；
- 安全、性能、兼容或数据负责人；
- 未来需要排障但没有原作者帮助的人。

这些视角是起点，不是数量限制。

### 5.3 未知记录格式

对高影响未知记录：

- 已知事实；
- 缺失信息；
- 重要原因；
- 可能影响；
- 验证方法；
- 验证前采用的保守假设；
- 负责人或所需资料；
- 当前状态。

可使用“待核实”“证据不足”“仅为推断”“需运行验证”“需维护者确认”“当前环境无法检查”等标签。

### 5.4 动态更新

发现新证据后：

- 修正旧结论，而不是为保持文档一致而忽略冲突；
- 更新覆盖图、未知记录和决策记录；
- 标明变更原因和影响；
- 检查是否需要回到前一阶段重新评估。

## 6. 独立判断与纠正

用户的想法是需求来源，不是自动成立的技术结论。

评估时重点判断：

- 用户理解是否符合代码与实际行为；
- 用户关注点是否真正高影响；
- 是否存在更深层根因或更重要遗漏；
- 想法是否破坏边界、兼容、稳定或维护性；
- 是否有更小改动、更低复杂度或更适合当前阶段的路径；
- 是否引入不必要的耦合、技术债务、资源消耗或长期负担；
- 某个“看似更强”的方案是否真的优于简单方案。

纠正或建议时说明：

- 结论；
- 证据；
- 影响范围；
- 收益、成本和风险；
- 替代方案；
- 判断可能失效的条件；
- 事实、推断和建议之间的区别。

不要迎合，也不要为了显得专业而夸大问题。

## 7. 认知基线、持久化记忆与阶段门槛

原项目认知基线应能让不了解项目的 Agent 快速建立正确心智模型，并保存到项目本身供后续 Agent 复用。具体目录、新鲜度判断、增量复查和写回协议见 `references/persistence-protocol.md`。

每次开始工作时先读取项目内已有记忆，比较其记录修订与当前分支、HEAD 和工作区。文档仍新鲜时复用；存在可界定变化时增量更新；历史失效、架构根本变化或证据冲突时重新建立基线。不要在没有版本核对的情况下盲目信任旧文档，也不要无视有效文档重复完整扫描。

基线完成后至少更新：

- 根入口与当前交接摘要；
- 原项目认知基线；
- 机器可读状态和对应修订；
- 文档变更日志。

提交认知基线后必须暂停，除非用户已在当前或此前对话中明确确认最终改造方向。不要把讨论中的候选想法提前写成最终架构。

决策记录至少区分：

- 已确认；
- 暂定；
- 被否决；
- 延后；
- 待验证；
- 被替代；
- 触发重新评估的条件。

实施期间持续保存工作项状态、修改位置、验证证据、未完成内容、阻塞和下一步。重要状态不得只存在于聊天记录中。

## 8. 融合方案要求

确认方向后，融合方案根据实际改动组织，最低考虑：

- 改造目标、范围和非目标；
- 新旧架构和运行流程的映射；
- 保留、修改、新增、移除的模块；
- 接口、数据、状态、配置和依赖变化；
- 修改位置、原因和连锁影响；
- 实施顺序、阶段边界和前置条件；
- 兼容、迁移、安全、性能和维护影响；
- 历史问题复现风险与可借鉴经验；
- 测试、验收、诊断、回退和失败处理；
- Agent 的自主权限与暂停确认点；
- 未解决未知和验证计划。

明确标注：原项目事实、证据推断、历史经验、确认决定、候选方案和待验证内容。

## 9. 停止标准

不以“清单填完”作为完成标准。当前阶段可提交时应满足：

- 主要运行链路能够被解释；
- 高影响模块、依赖、约束和历史问题得到覆盖；
- 关键判断可追溯；
- 重大未知已经暴露；
- 开放式范围外检查已经执行；
- 未检查区域被明确说明；
- 继续扩展主要增加低价值细节，不会显著改变决策。

“未知的未知”不能被证明已经全部发现。正确做法是降低漏掉高影响未知的概率，并诚实说明剩余边界。

## 10. 常见失败模式

避免：

- 只读 README，不读代码、测试和历史；
- 把文件列表当成架构说明；
- 把用户报告直接写成已确认 Bug；
- 把历史版本问题套到当前版本；
- 机械建立四类未知栏目后停止思考；
- 逐项回答提示词，却没有形成项目特定覆盖图；
- 为了“全面”罗列大量低价值信息；
- 未确认方向就开始修改或输出融合架构；
- 用模糊措辞隐藏资料不足；
- 把建议包装成事实，把推断包装成验证结果；
- 为迎合用户而忽略证据；
- 为表现独立而无依据反对用户；
- 每次调用都无视有效项目记忆重新扫描全部代码；
- 看到旧文档就不核对其对应分支和提交；
- 只在聊天中记录决定、完成项和未完成项；
- 代码已写入但未经验证就标记完成；
- 覆盖被否决、失败或被替代的历史，导致后续 Agent 重复走弯路。
