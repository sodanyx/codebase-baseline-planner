## 1. 目标

把项目分析、确认决策、融合方案和实施进度保存到项目本身，使后续 Agent 或新对话能够先读取既有认知，再根据代码变化做增量验证，而不是每次从零扫描。

持久化文档不是不可质疑的真相。它们是带版本、证据和覆盖边界的工作记忆。后续 Agent 必须检查其对应的分支、提交和更新时间，再决定直接复用、增量更新还是重新建立基线。

## 2. 默认文件结构

除非项目已有明确且更合适的文档规范，默认在项目根目录使用：

```text
AI_PROJECT_CONTEXT.md

docs/ai-project/
├── state.json
├── BASELINE.md
├── DECISIONS.md
├── FUSION_PLAN.md
├── IMPLEMENTATION_STATUS.md
└── CHANGELOG.md
```

职责如下：

- `AI_PROJECT_CONTEXT.md`：唯一稳定入口。保持简短，记录当前阶段、最后审查版本、下一步、阻塞项和详细文档链接。
- `state.json`：机器可读状态。记录基线、融合方案和实施状态所对应的 Git 修订，以及当前阶段和更新时间。
- `BASELINE.md`：原项目认知基线，只描述原项目事实、历史经验、推断、未知和覆盖边界。
- `DECISIONS.md`：用户想法的决策日志，保留已确认、暂定、否决、延后、待验证和被替代的历史。
- `FUSION_PLAN.md`：用户明确确认后的融合架构、实施顺序、测试和回退要求。未确认的想法不得写成最终方案。
- `IMPLEMENTATION_STATUS.md`：已完成、进行中、阻塞、未开始、取消和待验证工作，以及代码位置、提交、测试和下一步。
- `CHANGELOG.md`：记录上述文档发生的重要变化及原因，防止无痕覆盖旧认知。

项目已有 `AGENTS.md`、`CONTRIBUTING.md` 或专用架构目录时，不要复制整套内容到多个地方。保留上述入口，使用链接指向项目既有权威文档，或在不破坏原规范的前提下调整目录。始终保证后续 Agent 能从项目根目录快速找到入口。

## 3. 每次调用时的读取顺序

调用本 Skill 后，不要立即扫描整个仓库。按以下顺序开始：

1. 确定项目根目录、当前分支、HEAD 和工作区状态。
2. 查找并读取 `AI_PROJECT_CONTEXT.md`。
3. 读取 `docs/ai-project/state.json`。
4. 根据当前任务读取 `BASELINE.md`、`DECISIONS.md`、`FUSION_PLAN.md` 和 `IMPLEMENTATION_STATUS.md`。
5. 比较保存的修订与当前代码状态。
6. 决定无需重扫、增量复查或完整重建。

如果入口或状态文件缺失、损坏或明显互相矛盾，先修复项目记忆结构，再继续工作。

可用本 Skill 自带脚本：

```bash
python scripts/project_memory.py status --project-root <project-root>
python scripts/project_memory.py init --project-root <project-root>
python scripts/project_memory.py validate --project-root <project-root>
```

脚本路径应以 Skill 安装目录为准。脚本只创建结构和检查版本，不替代实际代码分析。

## 4. 新鲜度判断与增量扫描

### 4.1 可以直接复用的情况

满足以下条件时，优先读取旧文档，不重新进行完整扫描：

- 当前修订与 `last_reviewed_revision` 相同；
- 工作区没有相关未提交改动；
- 文档没有明显自相矛盾或待处理失效标记；
- 当前任务仍处于文档记录的项目范围内。

即使直接复用，也要抽查与本次任务最相关的代码位置，避免仅凭摘要继续工作。

### 4.2 应进行增量复查的情况

当前代码晚于已记录修订时：

1. 获取从已记录修订到当前 HEAD 的变更文件、提交和相关 PR；
2. 检查工作区未提交变化；
3. 将变化映射到基线中的模块、运行链路、接口、依赖、配置和测试；
4. 只重新调查受影响区域及其上下游；
5. 更新被新证据改变的结论、未知和风险；
6. 更新入口、状态文件和变更日志。

不能因为文件数量少就假定影响小。入口、依赖、公共接口、数据格式、构建配置、权限、迁移和核心状态机制的单文件变化可能需要广泛复查。

### 4.3 应完整或大范围重建的情况

出现以下任一情况时，不要盲目复用旧基线：

- 保存的修订在当前历史中不存在，或仓库发生 rebase、force-push、迁移；
- 变更跨越大量核心模块，无法可靠界定影响；
- 主入口、架构边界、技术栈、构建系统或公共 API 发生根本变化；
- 旧文档对应不同分支、不同版本或不同项目副本；
- 旧文档缺少证据位置、覆盖边界或关键运行链路；
- 代码、测试、历史记录与旧文档出现重大冲突；
- 用户明确要求重新审计。

## 5. 各阶段写回规则

### 5.1 原项目基线完成后

必须写入或更新：

- `BASELINE.md`；
- `AI_PROJECT_CONTEXT.md` 的当前阶段、版本、关键结论和下一步；
- `state.json` 的 `baseline_revision` 与 `last_reviewed_revision`；
- `CHANGELOG.md`。

只有达到认知基线完成标准后，才能把阶段标记为 `baseline-complete`。调查未完成时使用 `baseline-in-progress`，并把缺失范围写清楚。

### 5.2 讨论用户想法时

每个高影响想法使用稳定编号，例如 `DEC-001`。更新 `DECISIONS.md`，不得只把结论留在对话中。

记录：

- 用户真正想达到的结果；
- 当前状态；
- 依据和影响范围；
- 确认、否决或延后的原因；
- 替代方案；
- 需要重新评估的条件；
- 与相关未知、历史问题和实施项的链接。

不要删除被否决或被替代的记录。更新状态并保留原因，避免后续 Agent 重复提出已经讨论过的方案。

### 5.3 融合方案确认后

必须写入或更新：

- `FUSION_PLAN.md`；
- `DECISIONS.md` 中相关条目的最终状态；
- `AI_PROJECT_CONTEXT.md` 的当前计划和下一步；
- `state.json` 的 `fusion_plan_revision` 与当前阶段；
- `CHANGELOG.md`。

融合方案必须指向其依赖的基线版本和决策编号。后续基线发生高影响变化时，标记融合方案需要重新确认，而不是静默沿用。

### 5.4 实施过程中

每个可追踪工作项使用稳定编号，例如 `IMP-001`，持续更新 `IMPLEMENTATION_STATUS.md`。

状态至少区分：

- `not-started`；
- `in-progress`；
- `blocked`；
- `implemented-unverified`；
- `completed`；
- `cancelled`；
- `superseded`。

不得仅因为代码已经写入就标记 `completed`。完成至少需要记录：

- 对应决策或方案章节；
- 修改文件或提交；
- 实际验证方式和结果；
- 已知限制或未覆盖测试；
- 是否更新了基线、方案、配置和用户文档。

无法运行测试时标记 `implemented-unverified`，不要伪装为完成。

### 5.5 每次暂停或交接前

更新 `AI_PROJECT_CONTEXT.md` 和 `IMPLEMENTATION_STATUS.md` 的交接信息：

- 当前所处阶段；
- 最近完成了什么；
- 正在处理什么；
- 尚未完成什么；
- 当前阻塞和原因；
- 下一步最具体动作；
- 必须先阅读的文档或代码位置；
- 最近一次验证结果；
- 工作区是否存在未提交改动。

让新 Agent 无需依赖旧对话即可恢复任务。

## 6. 状态、编号与证据要求

使用稳定 ID 建立文档间引用：

- 决策：`DEC-001`；
- 未知或待核实：`UNK-001`；
- 风险：`RSK-001`；
- 实施项：`IMP-001`；
- 缺陷或回归：`BUG-001`。

不要在重新排序时修改既有 ID。

每项关键记录尽量包含：

- 状态；
- 来源或证据；
- 影响范围；
- 关联 ID；
- 最后更新时间；
- 下一步或关闭条件。

对证据保持区分：已验证事实、有依据推断、外部反馈、未知或待核实。

## 7. 冲突、失效与回滚

发现旧文档与代码冲突时：

1. 不要为了保持文档一致而忽略新证据；
2. 标出冲突和影响；
3. 判断是文档过期、代码回归、分支差异还是历史记录错误；
4. 修正文档并在 `CHANGELOG.md` 说明原因；
5. 若影响已确认方案或已完成工作，重新打开相关决策或实施项；
6. 保留必要的旧结论摘要，避免失去推理历史。

重要方案变化应记录回退路径。不要通过直接删除文档掩盖失败尝试。

## 8. 写入和版本控制边界

- 在本地项目可写时，默认把文档实际保存到项目，而不是只在聊天中输出。
- 写入前读取现有文档并进行合并，禁止无条件覆盖人工内容。
- 不在文档中保存密钥、令牌、个人隐私、内部凭证或不应进入仓库的敏感数据。
- 默认不创建 Git 提交、不推送、不开 PR，除非用户明确授权相应操作。
- 写入后报告新增或修改了哪些文件，以及它们是否已被 Git 跟踪。
- 如果项目只读或只有远程读取权限，明确说明无法持久化，并提供应写入的完整文件内容或补丁；不要声称已经保存。
- 如果用户希望这些记忆随克隆和换机器继续存在，应将其纳入版本控制并由用户或授权工作流提交。

## 9. 常见失败模式

避免：

- 每次调用都无视现有文档重新扫描整个项目；
- 看到旧文档就完全不核对代码版本；
- 只保存最终方案，不保存原项目基线和决策过程；
- 把所有进度留在聊天中；
- 用“完成”代替可验证的测试证据；
- 覆盖或删除被否决、延后和失败的历史记录；
- 入口摘要与详细状态长期不一致；
- 保存大量流水账，却没有当前阶段、下一步和阻塞信息；
- 自动提交或推送未经用户授权的项目记忆文件；
- 将敏感信息写进可版本控制文档。
