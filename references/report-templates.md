# 输出与项目记忆模板

这些是弹性模板。根据项目特性调整章节，合并低价值部分，并增加由证据暴露出的项目专属内容。所有长期有效的结论、决策和实施状态都应保存到项目中，不只保留在聊天回复里。

## 目录

1. 根入口与交接摘要
2. 项目特定覆盖图
3. 原项目认知基线
4. 想法评估与决策记录
5. 融合后的二次开发方案
6. 实施状态与交接记录
7. 文档变更日志

## 模板 A：根入口与交接摘要

保存位置：`AI_PROJECT_CONTEXT.md`

```markdown
# [项目名称] AI Project Context

> 后续 Agent 从这里开始。先核对当前分支、HEAD、工作区和 `docs/ai-project/state.json`，再决定复用、增量复查或重建。

## 当前状态

- 当前阶段：[baseline-in-progress / baseline-complete / ideas-under-review / fusion-plan-confirmed / implementation-in-progress / implementation-complete / maintenance]
- 当前分支：[分支]
- 当前 HEAD：[提交]
- 最后审查修订：[提交]
- 最后更新时间：[时间]
- 工作区状态：[干净 / 有未提交改动，简述]

## 先读这些

1. `docs/ai-project/BASELINE.md`
2. `docs/ai-project/DECISIONS.md`
3. `docs/ai-project/FUSION_PLAN.md`
4. `docs/ai-project/IMPLEMENTATION_STATUS.md`
5. `docs/ai-project/CHANGELOG.md`

## 当前交接

- 最近完成：[最重要结果]
- 正在进行：[当前工作]
- 尚未完成：[高优先级剩余项]
- 阻塞：[阻塞及原因]
- 下一步：[一个最具体、可执行动作]
- 最近验证：[测试或检查及结果]
- 必须注意：[最容易误判或破坏的事项]

## 新鲜度说明

[说明旧文档对应哪个修订，以及当前是否需要增量复查。]
```

保持此文件简短。详细事实、争论和流水记录放在对应文档中。

## 模板 B：项目特定覆盖图

可作为 `BASELINE.md` 的前置章节或独立临时工作区，不必长期单独保存。

```markdown
# [项目名称] 调查覆盖图

## 当前对象与版本

说明仓库、分支、标签、提交、工作区、运行环境、已有项目记忆和可访问资料。

## 高价值调查领域

对每个领域说明：调查目标、重要性、证据来源、已有覆盖、变化范围、当前状态和信息缺口。

## 项目专属补充方向

说明哪些内容没有出现在用户清单中，但因项目结构、技术领域或历史记录而必须调查。

## 当前覆盖限制

列出权限、资料、环境或时间造成的边界。

## 开放式复查结果

回答：脱离原清单后，又发现了哪些可能改变架构理解或后续决策的方向？
```

## 模板 C：原项目认知基线

保存位置：`docs/ai-project/BASELINE.md`

```markdown
# [项目名称] 原项目认知基线

## 文档状态

- 对应分支：[分支]
- 基线修订：[提交]
- 最后增量审查修订：[提交]
- 最后更新时间：[时间]
- 调查方式：[完整扫描 / 增量复查]
- 覆盖边界：[已覆盖和未覆盖范围]

## 结论摘要

用简洁语言说明项目是什么、如何运行、最关键结构、主要风险和当前认知边界。

## 项目目标与适用边界

说明实际用途、使用者、支持范围、非目标和默认假设。

## 架构与完整运行链路

结合模块关系和执行顺序，解释从启动、输入到结果、异常、恢复和退出的真实流程。

## 代码地图与关键约定

说明重要目录、文件、类、函数、接口、数据结构、配置、隐含规则和扩展点。

## 环境、依赖、构建与部署

只保留会影响理解、运行、修改和复现的内容。

## 测试、诊断与质量保障

说明可验证路径、覆盖缺口、日志、CI 和故障定位方法。

## GitHub 历史问题与可复用经验

对高影响 Issue、PR、Release、提交或 CI 记录说明：版本、触发条件、根因、解决方式、当前适用性和对二次开发的启示。

## 不宜随意修改的部分

解释核心边界、连锁影响和可能破坏的兼容关系。

## 证据状态

按需要区分：已验证事实、有依据推断、未证实反馈、未知或待核实。使用稳定 ID 记录高影响未知，例如 `UNK-001`。

## 高影响未知与验证计划

说明缺失信息、影响、验证方法、验证前的保守假设和关闭条件。

## 主动发现与独立判断

说明用户原始要求之外发现的重要内容，以及需要纠正或重新评估的理解。

## 自上次基线后的变化

记录增量复查涉及的提交、文件、模块及其对旧结论的影响。首次建立时标记为不适用。

## 覆盖边界与停止理由

说明调查了什么、没有调查什么，以及为什么当前可以提交而不是继续堆积细节。

## 等待讨论

明确暂停，不生成融合架构；列出最值得用户先思考或确认的少量关键问题。
```

原项目事实与用户改造决定必须分开。确认后的想法写入决策和融合方案，不要回填成“原项目本来如此”。

## 模板 D：想法评估与决策记录

保存位置：`docs/ai-project/DECISIONS.md`

每项高影响决定使用稳定 ID，不删除旧记录。

```markdown
## DEC-[编号]：[主题]

- 日期：[时间]
- 状态：[已确认 / 暂定 / 被否决 / 延后 / 待验证 / 被替代]
- 用户目标：[准确复述]
- 关联基线：[修订或章节]
- 影响范围：[模块、流程、接口、历史问题]
- 判断：[结论]
- 证据与理由：[代码、文档、测试、历史或逻辑]
- 收益：[收益]
- 成本与风险：[成本、风险、维护负担]
- 替代方案：[方案及取舍]
- 待验证内容：[未知或实验]
- 重新评估条件：[什么变化会改变决定]
- 关联实施项：[IMP-xxx]
- 更新历史：[状态变化和原因]
```

候选想法不得仅因为被讨论过就标记为已确认。

## 模板 E：融合后的二次开发方案

保存位置：`docs/ai-project/FUSION_PLAN.md`

```markdown
# [项目名称] 融合改造方案

## 文档状态

- 确认状态：[未确认 / 已确认 / 需要重新确认]
- 依赖基线修订：[提交]
- 相关决策：[DEC-xxx]
- 最后更新时间：[时间]
- 当前代码修订：[提交]

## 已确认目标、范围与非目标

只写用户已经明确确认的内容，候选设想另行标记。

## 新旧架构映射

说明原有结构、改造后结构、变化原因及不变部分。

## 运行流程与数据流变化

解释新的完整执行路径，不只列模块。

## 变更清单

按保留、修改、新增、移除组织，并说明位置、原因、依赖和连锁影响。

## 实施顺序与确认门槛

说明阶段、前置条件、依赖、可并行部分和必须暂停确认的位置。为可执行工作项分配 `IMP-xxx`。

## 兼容、迁移与历史问题防复现

结合仓库历史说明需要特别验证的风险和借鉴方式。

## 测试、验收、诊断与回退

给出可执行的验证标准、失败处理和回退路径。

## Agent 行为边界

区分可自主决定、需要记录、必须询问和禁止擅自改变的事项。

## 尚未解决的未知

保留未知和验证计划，不制造虚假完整性。

## 证据与决策追溯

明确区分原项目事实、推断、历史经验、确认决定和待验证内容。

## 重新确认条件

说明哪些基线变化、测试失败或需求变化会使本方案失效。
```

## 模板 F：实施状态与交接记录

保存位置：`docs/ai-project/IMPLEMENTATION_STATUS.md`

```markdown
# [项目名称] 实施状态

## 当前摘要

- 当前阶段：[阶段]
- 当前代码修订：[提交]
- 最近完成：[结果]
- 正在进行：[工作项]
- 下一步：[具体动作]
- 当前阻塞：[阻塞和原因]
- 最近验证：[测试及结果]
- 工作区状态：[干净 / 未提交改动]

## 工作项

| ID | 关联决策 | 工作内容 | 状态 | 文件 / 提交 | 验证证据 | 剩余工作 / 下一步 |
|---|---|---|---|---|---|---|
| IMP-001 | DEC-001 | [工作] | not-started | — | — | [下一步] |

允许状态：`not-started`、`in-progress`、`blocked`、`implemented-unverified`、`completed`、`cancelled`、`superseded`。

## IMP-[编号] 详细记录

- 目标：[目标]
- 关联方案：[章节或 DEC]
- 实际修改：[文件、接口、配置]
- 当前状态：[状态]
- 验证：[命令、测试、人工检查、结果]
- 已知限制：[限制]
- 未完成：[剩余工作]
- 阻塞：[阻塞及解除条件]
- 下一步：[一个具体动作]
- 最后更新：[时间与修订]

## 已知缺陷和回归

使用 `BUG-xxx` 记录症状、触发条件、影响、诊断、状态和关联工作项。

## 交接说明

说明新 Agent 必须先读什么、从哪里继续、不要重复做什么、哪些判断尚未确认。
```

只有具备代码和验证证据的项目才能标记 `completed`。无法验证时使用 `implemented-unverified`。

## 模板 G：文档变更日志

保存位置：`docs/ai-project/CHANGELOG.md`

```markdown
| 日期 | 源代码修订 | 修改文档 | 变化原因 | 影响的决定 / 工作项 | Agent / 作者 |
|---|---|---|---|---|---|
| [时间] | [提交] | BASELINE.md | 增量复查发现入口流程改变 | DEC-002, IMP-004 | [标识] |
```

只记录会影响后续理解、决策或实施的变化。不要把每个标点修正都写成一条日志。
